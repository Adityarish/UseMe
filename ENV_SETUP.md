# Environment setup

Use `.env.local` for real credentials. It is ignored by Git. Keep `.env.example` as a secret-free template.

The quickest local setup is:

```bash
python3 run.py
```

On its first run, the launcher copies `.env.example` to `.env.local`, generates independent random values for `APP_SECRET` and `CLEANUP_SECRET`, installs missing npm dependencies, starts PostgreSQL with Docker Compose, applies the database migration, and starts the Next.js development server.

Before running it, install Node.js 22 or newer and Docker Desktop, then start Docker Desktop. Python 3 uses only its standard library, so there are no Python packages to install.

## Values that work locally without external accounts

| Variable | Local value | How to choose it |
| --- | --- | --- |
| `APP_URL` | `http://localhost:3000` | Server-only canonical app origin; keep this exact origin while running locally. |
| `DATABASE_URL` | `postgresql://useme:useme@localhost:5432/useme` | Matches the PostgreSQL service in `docker-compose.yml`. |
| `APP_SECRET` | generated by `run.py` | A private random value of at least 32 characters used to sign access cookies. |
| `STORAGE_PROVIDER` | `local` | Uses private local disk storage during development. |
| `LOCAL_STORAGE_PATH` | `.local-storage` | The ignored directory where local uploads are stored. |
| `MAX_CLIP_BYTES` | `52428800` | 50 MiB total attachment limit per clip. |
| `MAX_FILES_PER_CLIP` | `20` | Maximum attachment count per clip. |
| `UPLOAD_SESSION_MINUTES` | `60` | Lifetime of an unfinished upload session. |
| `ONE_TIME_SESSION_MINUTES` | `10` | Download window after a one-time clip is claimed. |
| `ANONYMOUS_MAX_EXPIRY_DAYS` | `30` | Maximum retention available to guest users. |
| `CLEANUP_SECRET` | generated by `run.py` | A separate private random value protecting the cleanup endpoint. |
| `TRUSTED_PROXY` | `false` | Keep false locally. Set true only when a trusted reverse proxy overwrites forwarding headers. |

You can also generate either secret manually with `openssl rand -base64 48`.

## Supabase account values (optional)

Leave both Supabase values blank to run in Guest mode. To enable email/password sign-up, Google sign-in, ownership, Forever links, and the dashboard:

1. Create a project in the [Supabase Dashboard](https://supabase.com/dashboard).
2. Open **Project Settings → API Keys**. Copy the Project URL to `NEXT_PUBLIC_SUPABASE_URL` and the publishable key to `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
3. Under **Authentication → URL Configuration**, use `http://localhost:3000` as the Site URL and allow `http://localhost:3000/auth/callback`.
4. Email/password authentication is enabled from **Authentication → Providers → Email**.
5. For Google, enable the Google provider in Supabase, copy its callback URL, and add that exact URL as an authorized redirect URI on a Google Web OAuth client. Save that client's ID and secret in the Supabase provider settings, not in UseMe's environment.
6. Restart `python3 run.py` after changing a `NEXT_PUBLIC_*` value.

For production, add `https://your-domain/auth/callback` to Supabase's redirect allow list and set the Site URL to the deployed HTTPS origin.

## Google Drive values (production storage)

These four values are required only when `STORAGE_PROVIDER=google-drive`. Use a dedicated Google account or an appropriate Google Workspace account rather than a personal Drive containing unrelated files.

1. In [Google Cloud Console](https://console.cloud.google.com/) create or select a project and enable **Google Drive API**.
2. Open **Google Auth Platform**. Configure Branding and Audience. If the audience is External and the app is in Testing, add the dedicated storage account as a test user.
3. Under **Data Access**, add `https://www.googleapis.com/auth/drive.file`. This is the narrow per-file Drive scope used for files the app creates.
4. Under **Clients**, create a **Web application** OAuth client. Add this exact authorized redirect URI: `https://developers.google.com/oauthplayground`.
5. Save the client ID as `GOOGLE_CLIENT_ID` and client secret as `GOOGLE_CLIENT_SECRET`.
6. Open [Google OAuth 2.0 Playground](https://developers.google.com/oauthplayground/). Select the gear icon, enable **Use your own OAuth credentials**, enter the same client ID and client secret, and close the settings panel.
7. In Step 1, enter `https://www.googleapis.com/auth/drive.file`, authorize it, and sign in as the dedicated storage account.
8. In Step 2, exchange the authorization code for tokens. Copy the refresh token into `GOOGLE_REFRESH_TOKEN`; do not use the short-lived access token.
9. While the Playground token is active, use Step 3 to create the app-owned root folder:
   - Method: `POST`
   - Request URI: `https://www.googleapis.com/drive/v3/files?fields=id`
   - Content-Type: `application/json`
   - Body: `{"name":"UseMe Storage","mimeType":"application/vnd.google-apps.folder"}`
10. Send the request and copy the returned `id` into `GOOGLE_DRIVE_ROOT_FOLDER_ID`.
11. Set `STORAGE_PROVIDER=google-drive`, restart the app, upload a test file, download it, and delete it before relying on this configuration. The app creates `Storage1`, `Storage2`, and `Storage3` inside the root folder and distributes new binary attachments across them.

Use your own OAuth client in the Playground. Playground-owned refresh tokens are automatically revoked after 24 hours. Google also documents that refresh tokens for an External consent screen left in Testing commonly expire after seven days; move a real deployment to the appropriate production/verified state.

### Why Drive still needs a refresh token

The Google client ID identifies the OAuth application and the client secret proves which backend is making the token request. Neither value grants access to a Google account or Drive folder. Drive API calls require a short-lived access token; the server uses the dedicated storage account's refresh token to obtain new access tokens without asking a person to sign in every hour.

Supabase's Google button is a user-login flow with identity scopes. It is intentionally separate from the dedicated Drive storage flow. Reusing each visitor's Google provider token would store files in different user accounts, request broader consent, and still require provider-token refresh handling. A single server-only Drive refresh token is the simpler model for one shared `UseMe Storage` folder.

## Malware scanner values (not implemented yet)

Leave `MALWARE_SCAN_WEBHOOK_URL` and `MALWARE_SCAN_WEBHOOK_SECRET` blank. They are reserved configuration names; the current upload path does not call a scanner. Filling them in alone does not enable malware scanning.

## Production-only changes

- Set `APP_URL` to the exact public HTTPS origin with no path. This is server-only configuration, not a secret.
- Use a managed `DATABASE_URL` supplied by your PostgreSQL provider, normally with TLS enabled.
- Set `STORAGE_PROVIDER=google-drive` and provide all four Google values.
- Store every secret in the hosting provider's secret manager, not in a committed file.
- Set `TRUSTED_PROXY=true` only after confirming the proxy replaces untrusted forwarding headers.
- Schedule `npm run cleanup` at least every 10 minutes and supply the same runtime environment variables.

## Vercel values

Use [.env.vercel.example](./.env.vercel.example) as the variable-name checklist. Add the values in **Vercel → Project Settings → Environment Variables** rather than committing a real file. Use the Supabase transaction-pooler URL for `DATABASE_URL`; keep a direct or session-pooler URL as `MIGRATION_DATABASE_URL` for the one-time migration command. Vercel Functions have a 4.5 MB payload limit, so this deployment profile sets `MAX_CLIP_BYTES=4000000`.
